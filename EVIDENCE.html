Technical Evidence

Proof-of-Solvency for Tokenized Private Credit

A fund proves a coverage and KYC predicate over a supplied private loan book without revealing individual loans. Local pilot alpha with reproducible tests and explicitly scoped network evidence.

What it is

An open-source zero-knowledge verifier. A Groth16/BN254 circuit proves, over a PRIVATE loan book, that (1) performing collateral covers a public threshold, (2) every supplied KYC flag is true, and (3) the private witnesses hash to a blinded public commitment. Only the threshold and commitment are revealed. A legacy native model checks a proof and a servicer signature over the same commitment. The separate local pilot gate pins the key and servicer and records a policy-checked approval receipt; it does not mint tokens or establish that the off-chain data is true.

Developer-run verification and historical code reviews

1. Empirical adversarial audit (cargo run --bin audit): checks that fail if the ZK claims were fabricated. Result: the circuit genuinely enforces solvency, all-KYC, and commitment binding; insolvent, KYC-fail, and wrong-commitment books each fail the constraint system; a proof with one flipped bit or an altered public input is rejected. Passed.

2 & 3. Historical code-review passes. Their findings and follow-up are recorded in AUDIT.md. These reviews prompted documented fixes; they were not a formal third-party security audit. The newer pilot evidence is developer-run regression evidence.

Reproducible

./demo.sh runs unit tests, loan-tape decisions, proof checks, the native signature-binding model, 100/1,000-loan benchmarks and the SBF compute measurement. Run cargo run --release --bin audit and cargo run --release --bin bench -- 10000 separately. Public receipts are checked separately. MIT-licensed; logs are in DEPLOYMENTS.md.

What is NOT yet production-safe (stated honestly)

  • Trusted setup is not yet fully multi-party. The pinned compatibility rehearsal checks locally generated phase-1 and phase-2 artifacts, but all contributors are controlled by one operator. A production ceremony needs independently operated contributors and reviewed parameter provenance.
  • On-chain mint integration is incomplete. The legacy example accepts a caller-supplied key. The separate local pilot gate pins the key and servicer and enforces threshold, freshness and sequence, but it does not use live token supply, mint SPL tokens or prevent repeated downstream use of one receipt.
  • Not third-party security-audited. Historical review findings are recorded in the repository, but no formal third-party security audit has been performed.
  • The data-trust anchor is external. A proof certifies that the servicer-attested data is solvent, not that the data is true. It depends on an authenticated signed loan-tape feed.

Full detail: KNOWN_LIMITATIONS.md. This is a local pilot alpha, not a production system.
